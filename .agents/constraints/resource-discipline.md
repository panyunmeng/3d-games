# 资源纪律（浏览器 / 构建 / 子代理）

> 2026-11-18 用户明确投诉：「你使用 chrome 了吗？这玩意儿 CPU 占用都 70% 了」。
> 实测：一次 CDP 验收会拉起 **13 个** `chrome.exe` 进程（主进程 + 渲染 + GPU +
> 若干 utility），常驻之后叠加脚本，CPU 直接打满。

## 一、浏览器（最难容忍的一条）

1. **禁止后台常驻浏览器**。不要写 `chrome.exe ... &` 或 `Start-Process` 把它挂起来
   等后续多次复用——那 13 个进程会一直吃 CPU，即使标签页是 `about:blank`。
2. 验收工具必须**自己 spawn、自己 kill**，并在一轮跑完后核对归零：
   ```powershell
   Get-Process chrome -ErrorAction SilentlyContinue | Measure-Object | Select-Object Count
   ```
   非 0 就 `Stop-Process -Force`。
3. **一个脚本内复用同一个浏览器实例**：切换视口用
   `Emulation.setDeviceMetricsOverride`，不要每个游戏/每个视口重开浏览器
   （重开一次 = 13 个进程再起一遍）。
4. 用完删掉临时的 `--user-data-dir` profile 目录，否则下次启动会复用它、
   越攒越多。
5. 需要「验完还要继续验」时，**不要**留一个常驻实例给我；改为把该脚本一次跑完
   （脚本内部循环所有目标）。

## 二、子代理

1. 批量派子代理做同类任务时，任务书里必须写清资源纪律：
   - 不要为验收各自独立起浏览器（改为：由**主代理统一跑**一次全量验收）；
   - 不要各自重复 `pnpm install` / 重复全量构建；
   - 不许后台挂常驻进程；收工时清理自建进程与临时目录。
2. 验证动作尽量**收归主代理**：子代理只改代码 + 跑类型检查/单测（这些轻量），
   浏览器类验收由主代理串行跑一遍。子代理并发开浏览器是本轮 CPU 打满的直接原因。
3. 同一时刻并发的重活（构建、浏览器）不超过 2 个。

## 三、构建

- 各游戏的 `dist/` 只在需要验产物时才重建；同一轮里不要反复全量构建。
- 平台 `scripts/build.mjs` 很快（0.1s），这个可以随便跑。
- `pack.mjs` + `deploy.mjs` 涉及上传，一轮只做一次。
